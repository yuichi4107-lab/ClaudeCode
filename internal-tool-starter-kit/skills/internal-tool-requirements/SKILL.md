# Internal Tool Requirements

## 使う場面

社内ツールの新規作成、機能追加、仕様変更、運用変更の前に使う。

小さな文言修正や明らかなバグ俭正でも、扱うデータ・権限・本番影響がある場合はこのスキルで要件を整理する。

## 基本方針

社内ネットワーク内のツールでも安全とはみなさない。実装前に、何を作るかだけでなく、誰が使い、どのデータを扱い、どの操作が危険かを明確にする。

## 手順

1. 現状を確認する。
   - `README.md`
   - `AGENTS.md`
   - 既存の仕様書、TODO、引き継ぎメモ
   - 関連コード、設定、テスト
   - 現在のGit差分

2. 日付が関係する場合は、推測せずツールで確認する。

3. 要件定義書を作る。
   - ゴール
   - 背景
   - 利用者
   - スコープ
   - スコープ外
   - 入力データ
   - 出力データ
   - 保存するデータ
   - データ分類
   - 認証・権限要件
   - 外部通信の有無
   - 破壊的操作の有無
   - 完了条件
   - 品質基準
   - 工程分割
   - 承認が必要な判断

4. 承認ゲートを明示する。
   - 認証・権限に関わる変更
   - 個人情報・顧客情報・機密情報に関わる変更
   - 外部サービス連携
   - 本番環境・共有DBへの変更
   - データ削除、移行、一括更新
   - セキュリティ設定の緩和

5. ユーザー承認が必要な場合は、実装前に止める。

## 出力形式

```md
# 要件定義

## ゴール

## 背景

## 利用者

## スコープ

## スコープ外

## 扱うデータ

## 認証・権限

## 外部通信

## 破壊的操作

## 完了条件

## 品質基準

## 工程分割

## 承認が必要な事項
```

## 禁止事項

- 「社内ツールだから安全」とみなす
- 扱うデータを確認せず実装する
- 権限要件を曖昧なままにする
- 本番・共有DBへの影響を確認せず進める
- ユーザー承認が必要な変更を勝手に実装する
