# Internal Tool Handoff

## 使う場面

社内ツールの作業終了時、中断時、担当者交代時、レビュー依頼時、リリース前の引き継ぎ時に使う。

## 基本方針

引き継ぎは「次の担当者が安全に再開できる状態」を作るために書く。成果だけでなく、未完了、未検証、承認待ち、残リスクを明記する。

## 手順

1. 作業範囲を確認する。
   - 依頼内容
   - 実施した工程
   - スコープ外にした内容
   - ユーザー承認が必要だった判断

2. 変更内容を整理する。
   - 変更ファイル
   - 追加ファイル
   - 削除ファイル
   - 設定変更
   - データ変更
   - 外部サービス設定変更

3. 検証結果を整理する。
   - 実行したテスト
   - 実行した手動確認
   - 実行できなかったテスト
   - 確認できなかった理由

4. セキュリティと運用リスクを整理する。
   - 秘密情報を含めていないか
   - 個人情報や顧客情報を含めていないか
   - 権限や本番操作の承認待ちがないか
   - 破壊的操作やデータ移行の残リスクがないか

5. 次アクションを具体化する。
   - 次にやること
   - 誰の承認が必要か
   - どのファイルを見るべきか
   - どのコマンドで確認するか

6. 日付を記録する場合は絶対日付にする。

## 出力形式

```md
# 引き継ぎ

## 日付

YYYY-MM-DD

## 作業概要

## 変更ファイル

## 実施した確認

## 実施できなかった確認

## 判断・決定事項

## 残リスク

## 承認待ち

## 次アクション

## 注意事項
```

## 禁止事項

- パスワード、APIキー、トークン、秘密鍵を書く
- 個人情報や顧客情報の実データを書く
- 未検証なのに検証済みと書く
- 未完了なのに完了扱いにする
- 本番反映や削除操作の承認状態を曖昧にする
- 長大なログをそのまま貼る
