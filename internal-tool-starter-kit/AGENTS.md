# 社内ツール開発ルール

## 1. 基本方針

このプロジェクトは、企業内ネットワークで利用する社内ツールの開発を前提とする。

ただし、社内利用であっても安全とはみなさない。認証、権限管理、ログ管理、秘密情報管理、外部送信制御を必ず確認する。

## 2. 作業前の確認

作業開始前に以下を確認する。

- `README.md`
- `AGENTS.md`
- 既存の仕様書、設計書、TODO、引き継ぎメモ
- 関連する設定ファイル
- 既存のテスト
- 現在のGit差分

日付・曜日が関係する処理では、推測せずツールやコマンドで確認する。

## 3. 作業フロー

すべての作業は次の順で行う。

```text
要件定義 → 実行 → 品質チェック → 報告
```

要件定義では以下を明確にする。

- ゴール
- スコープ
- スコープ外
- 完了条件
- 扱うデータ
- 認証・権限
- 外部通信
- 破壊的操作
- 品質基準

認証、権限、個人情報、外部通信、本番環境、データ削除に関わる変更は、実装前に人間の承認を得る。

## 4. 使用するスキル

必要に応じて以下のスキルを使用する。

```text
internal-tool-requirements
  新規開発、仕様変更、機能追加の前に使用する。

internal-tool-security-review
  認証、権限、個人情報、ログ、外部通信に関わる作業で使用する。

internal-tool-quality-check
  実装後、リリース前、研修課題の確認時に使用する。

internal-tool-handoff
  作業終了時、中断時、担当者交代時に使用する。

internal-tool-scaffolder
  新しい社内ツールの雛形を作るときに使用する
```

## 5. セキュリティ禁止事項

以下は禁止する。

- パスワード、APIキー、トークン、秘密鍵をコードに直書きする
- `.env`、認証情報、秘密鍵、社内限定資料をGitにコミットする
- 機密情報、個人情報、顧客情報をログにそのまま出力する
- 社内データを外部サービス、外部API、クラウド、AIサービスへ無断送信する
- 認証、認可、権限チェックを省略・迂回する
- TLS証明書検証、CSRF対策、入力検証を理由なく無効化する
- 本番DBや共有ストレージに対して、確認なしに削除・更新・移行処理を行う
- `rm -rf`、`git reset --hard`、DB全削除などの破壊的操作を確認なしに実行する
- 外部依存パッケージを理由なく追加する
- 「社内ツールだから」という理由で安全対策を省略する

## 6. 実装ルール

- 既存の設計、命名、ディレクトリ構成に合わせる
- 不要な大規模リファクタリングをしない
- 入力値はサーバー側で検証する
- 権限チェックは画面側だけでなくサーバー側にも実装する
- エラー時に秘密情報を表示しない
- ログには必要最小限の情報だけを出す
- 設定値は環境変数または安全な設定管理に分離する
- 重要処理には監査ログを残す
- データ変更処理には確認、バックアップ、ロールバック方法を考慮する

## 7. 品質チェック

作業後に以下を確認する。

- 要件を満たしている
- 既存機能を壊していない
- テストが通る
- 入力検証がある
- 権限チェックがある
- 秘密情報がログや画面に出ない
- 外部通信が必要最小限である
- エラー時の挙動が安全である
- 操作ミスで重大なデータ破壊が起きにくい

品質チェックは100点満点で採点し、85点以上を合格とする。

## 8. ターミナル出力制限

- ログ出力は最大200行まで
- 巨大ファイルは直接表示しない
- `node_modules`、ビルド成果物、大容量ログは表示しない
- base64、秘密情報、個人情報を表示しない
- 長い結果はファイルに保存し、画面には要約だけ出す

## 9. 完了報告

完了時は以下を報告する。

- 何を変更したか
- どのファイルを変更したか
- どのテスト・確認を実施したか
- 残っているリスク
- 次に人間が確認すべきこと
