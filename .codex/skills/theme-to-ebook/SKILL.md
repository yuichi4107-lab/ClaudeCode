# Theme-to-Ebook

テーマまたは添付素材を起点に、KDP出版向けの文字中心電子書籍を企画・執筆・画像生成・メタデータ作成まで進める。
出力は `ebook-to-manga` の入力ソースとしてそのまま使える構成にする。

> **Claude側 `ebook-from-theme` との使い分け（意図的な別実装）**: 本スキルは Codex 側の実装で、既定 100,000字（25,000/50,000/100,000字）・7パート構成・`progress.json` 方式。Claude Code 側には別実装の `ebook-from-theme`（既定 25,000字・`image_plan.json` 方式）がある。両者は実行環境の思想差（Claude=対話型、Codex=無人自律完走型）に基づく意図的な別実装であり、仕様を相互に同期しない。Codex 側では本スキルを文字中心電子書籍制作の正本とする（2026-07-07 オーナー承認）。

## 最重要ルール: 初回質問後に自動進行

このスキルは「初回に選択UIで制作条件を確認し、その後はKDP用成果物とマンガ化用ソースの完成まで自動進行する」ことを最優先の運用ルールとする。

- Phase 0の質問項目・選択肢の意味は従来どおり扱う。変更してよいのは「質問の出し方」と「回答の受け取り方」だけ。
- Phase 0では、利用可能な場合は必ず `request_user_input` のクリック式選択UIを使う。
- クリック式UIの1回あたり質問数に制限がある場合は、従来の質問セットを複数回に分けて提示する。質問項目そのものを削らない。
- 推奨案のラベルには必ず `(Recommended)` を付ける。
- `request_user_input` が利用できない実行環境では、Markdownの代替質問へ勝手に切り替えない。代わりに `.company/scripts/ebook_setup_ui.py` のローカルクリック式フォームを起動し、ブラウザで選択してもらう。
- Phase 0の回答が不足している場合は、不足項目だけ短く再質問する。
- 判断に迷う仕様・範囲・優先順位が途中で出た場合も、クリック式UIで短く確認する。
- 軽微な判断は止まらず、Phase 0回答とStep 0リサーチから妥当な前提を置いて進める。
- Phase 0を通過したら、Step 0（テーマリサーチ）を必ず実行してから Step 1 に入る。
- Step 1以降は、途中で承認・確認・選択を求めず自動進行する。
- 著者名・想定読者・文体・画像密度・出力フォルダ名が未指定の場合は、Phase 0回答とStep 0リサーチから合理的に自動決定する。
- Step 1の企画案とStep 2のアウトラインは、ユーザー提示用の中間成果物ではなく、内部要件定義として保存して即次Stepへ進む。
- 品質ゲートは自動実行する。85点未満または不備検出時は最大5回まで自動修正し、再失敗時は `warnings` に記録して次Stepへ進む。
- 停止してよいのは、必須情報・実行権限が欠けて処理不能な場合、ChatGPT/Codex側の画像生成が利用不能な場合、またはユーザーが明示的に停止を指示した場合のみ。
- 高リスク領域（医療・健康・投資・法律など）は停止ではなく、断定回避・免責・根拠表現の自動強化で対応する。

## 入力

- **テーマまたは添付素材**（必須）: 例「地方中小企業のAI活用」「40代からのキャリア再設計」、文字起こし、メモ、既存原稿など
- **Phase 0回答**（必須）: クリック式選択UIの回答。未回答なら制作開始前に質問する
- **著者名**（任意）: 未指定時はテーマ・読者層に合う著者名または既定値を自動採用する
- **出力フォルダ名**（任意）: 未指定時はテーマから英数字スラッグを作る

## Phase 0: 初回質問UI

スキル起動直後、リサーチやStep 1に入る前に、クリック式選択UIでユーザーの回答を待つ。`request_user_input` が使える場合は各質問を独立した選択カードとして提示する。使えない場合は `.company/scripts/ebook_setup_ui.py` を起動し、ローカルブラウザフォームで同等の選択肢を提示する。質問項目・選択肢の意味は従来のPhase 0から変えない。

**クリック式UIの必須仕様:**
- 1回に出せる質問数が1〜3問までの場合は、Phase 0を2回に分けて提示する。
- 1回目: テーマの扱い、想定読者、本の型。
- 2回目: 文体、文字量、画像密度。
- 推奨案は先頭に置き、ラベル末尾に `(Recommended)` を付ける。
- クリック式UIの選択肢数に制限がある場合は、従来の推奨案と主要な代替案を表示し、表示しきれない既存選択肢はUI側の `Other` または短い補足確認で受け取る。
- 自由記述は、全クリック回答後に短く補足確認する。UI側が `Other` を自動追加する場合はそこでも受け取ってよい。
- ユーザーに `1A、2B...` のようなテキスト回答を要求しない。クリックで選ばせる。

**クリック式UIの出し方:**

1回目の `request_user_input`:

- `theme_handling`: テーマの扱い
  - 入力内容のテーマで進める (Recommended)
  - 入力内容を少し広げて進める
  - 入力内容を絞り込んで進める
- `target_reader`: 想定読者
  - 初心者・これから始める人 (Recommended)
  - 中小企業の経営者・管理職
  - 実務担当者・現場リーダー
- `book_type`: 本の型
  - 実践書・手順書 (Recommended)
  - やさしい入門書
  - ストーリー・事例中心

2回目の `request_user_input`:

- `tone`: 文体
  - やさしいです・ます調 (Recommended)
  - 端的でビジネス寄り
  - 親しみやすい会話調
- `length`: 文字量
  - 約100,000字 (Recommended)
  - 約50,000字
  - 約25,000字
- `image_density`: 画像密度
  - 標準（章ごとに数点） (Recommended)
  - 少なめ
  - 図解中心

**ローカルフォームの出し方（`request_user_input` が使えない場合）:**

```bash
python3 .company/scripts/ebook_setup_ui.py --theme "{テーマ}" --mode theme-to-ebook
```

- サーバーは `127.0.0.1` の空きポートで起動する
- 表示された `ebook_setup_ui_url=...` をユーザーへ案内する
- ユーザーが保存すると `.company/outputs/ebook-setup-inputs/latest.json` に回答が保存される
- 回答を読み取り、`progress.json` の `initial_questions` に `ui: "local_clickable_form"` として保存する

**質問セット（内容は従来どおり）:**

1. テーマの扱い
   - 入力内容のテーマで進める (Recommended)
   - 入力内容を少し広げて進める
   - 入力内容を絞り込んで進める
   - 別テーマを指定する

2. 想定読者
   - 初心者・これから始める人 (Recommended)
   - 中小企業の経営者・管理職
   - 実務担当者・現場リーダー
   - 専門家・上級者

3. 本の型
   - 実践書・手順書 (Recommended)
   - やさしい入門書
   - ストーリー・事例中心
   - 考え方・思想を伝える本

4. 文体
   - やさしいです・ます調 (Recommended)
   - 端的でビジネス寄り
   - 親しみやすい会話調
   - 専門家らしい落ち着いた文体

5. 文字量
   - 約25,000字
   - 約50,000字
   - 約100,000字 (Recommended)
   - 自由記述で指定

6. 画像密度
   - 標準（章ごとに数点） (Recommended)
   - 少なめ
   - 多め
   - 図解中心

テーマ自体が不明な場合は、上記よりも先に「扱うテーマ」を確認する。テーマ確認もクリック式UIを優先し、自由入力が必要な場合のみ短く補足を求める。

**回答処理ルール:**
- ユーザーが「お任せ」「推奨で」「デフォルトで」と回答した場合は、各質問のRecommendedを採用する。
- 自由記述は選択肢より優先する。たとえば選択肢が初心者向けでも、自由記述に「経営者向け」とあれば読者設定に反映する。
- テーマが不明な場合は、先にクリック式UIまたは短い補足確認でテーマを確定する。
- 回答が揃ったら、採用した前提と短い作業計画を提示してからStep 0へ進む。追加承認待ちで停止しない。
- 確定した回答は `progress.json` の `initial_questions` に保存する。

## 前提条件

- 画像生成に `OPENAI_API_KEY` は使わない
- 挿絵・図解は ChatGPT Images 2.0（Codex/ChatGPT側の画像生成経路）で生成する
- OpenAI API / `client.images.generate` / `client.images.edit` / `openai-image-gen` は使わない
- 画像は PNG で保存する
- 長編原稿は章単位で分割生成し、進捗を `progress.json` で管理する

## 文字版ポリシー

このワークスペースでユーザーが「文字中心」「文字版」「完全文字版」と言った場合は、漫画パートを含まないテキスト主体の電子書籍として扱う。

- 漫画ページ、章末漫画、漫画風ストーリーパネルを本文に混ぜない
- 画像密度の指定は、写真、図解、年表、表、概念図、ポップなアニメ・マンガ調の挿絵の量として扱う
- 画像は本文を補助するために入れる。画像下に「図解: ○○」のような表示キャプションを自動で出さない
- Markdown画像のaltテキストやEPUBのalt属性はアクセシビリティ用の短い説明に留め、ビューア上に `figcaption` として表示しない
- 図解は、その節・段落で実際に説明している内容と対応させる。本文の流れと関係が薄い共通図解を画像点数合わせで繰り返し挿入しない
- 自分史など個人情報を含む案件では、本人・家族提供写真や年表を使う場合のみ明示的に記録する
- 漫画版が必要な場合は、完成した文字版を別工程で `theme-to-ebook-to-manga` または `ebook-to-manga` に渡す
- `progress.json` には `edition_policy.text_edition = "complete_text_only"` または同等の記録を残す

## 標準構成

全体文字数はPhase 0の回答に従う。未指定時は約100,000字を基本とするが、出版スピードを優先する場合は25,000字または50,000字も選べる。

| 選択 | 全体目安 | 用途 |
|---|---:|---|
| 25,000字 | 22,500〜27,500字 | 短め・素早く出版 |
| 50,000字 | 45,000〜55,000字 | 標準的な実用書 |
| 100,000字 | 80,000〜120,000字 | 本格書籍 |

100,000字選択時の標準構成:

| パート | 文字数目安 | 役割 |
|---|---:|---|
| はじめに | 3,000〜5,000字 | 読者の悩み、読む理由、本書の約束 |
| 第1章 | 17,000〜19,000字 | 問題提起、現状整理 |
| 第2章 | 17,000〜19,000字 | 原因・背景・誤解の整理 |
| 第3章 | 17,000〜19,000字 | 中核ノウハウ、考え方 |
| 第4章 | 17,000〜19,000字 | 実践手順、事例、応用 |
| 第5章 | 17,000〜19,000字 | 定着、継続、未来像 |
| おわりに | 3,000〜5,000字 | 行動喚起、読後感、著者メッセージ |

25,000字・50,000字の場合も7パート構成は維持し、上記比率を保って各章の文字数を圧縮する。

## 実行フロー

## 全工程品質ループ

各Stepは必ず「要件定義 → 実行 → 品質チェック」の順で進める。ただし要件定義と品質チェックはスキル内部で自動実行し、ユーザー承認待ちで停止しない。

- Stepごとに完了条件と品質基準を明示する
- 各Stepの要件定義は `progress.json` または工程メモに保存し、承認待ちにせず次Stepへ進む
- 品質チェックは100点満点で採点する
- **85点以上で合格**、84点以下は改善して再チェックする
- 各Stepの改善ループは最大5回まで。5回を超える場合は警告を記録し、処理不能でなければ次Stepへ進む
- 医療・健康・投資・法律など高リスク領域では、断定表現、根拠不足、危険な行動誘導を重点確認する

標準Step別の品質観点:

| Step | 品質チェック観点 |
|---|---|
| 0 テーマリサーチ | 競合、読者ニーズ、現在性、差別化ポイント、リスク領域が把握できているか |
| 1 企画確認 | 読者、目的、トーン、リスク表現、出版方向性が明確か |
| 2 詳細アウトライン | 5章構成、論理展開、10万字化できる密度、画像案が十分か |
| 3 project.md | `ebook-to-manga` に接続できるメタ情報が揃っているか |
| 4 本文執筆 | 文字数、読みやすさ、章内構成、具体例、根拠表現、安全性が満たされているか |
| 5 画像設計 | 本文対応、配置、過不足、繰り返しの不自然さ、誤解を招かない表現になっているか |
| 6 画像生成 | PNG保存、本文対応、視認性、アニメ・マンガ調の画風とキャラ統一、表示キャプションなし、危険・誤認表現の回避ができているか |
| 7 KDPメタデータ | KDPで使える形式、キーワード、紹介文、安全表現、表紙PNG/JPEGが揃っているか |
| 8 最終品質チェック | 全ファイル、総文字数、画像リンク、構成、マンガ化適性が揃っているか |

### Step 0: テーマリサーチ

Phase 0の回答で確定したテーマについて、Step 1の企画決定前に必ずリサーチする。テーマが添付素材由来の場合は、添付内容から主要論点を抽出してから検索クエリを作る。

**リサーチ対象:**
- 現在の市場・社会的背景
- 読者が抱えている悩み、検索意図、よくある誤解
- 競合書籍・類似コンテンツの切り口
- 専門家・実務家の主要論点
- 2026年時点で更新が必要な制度、技術、トレンド
- 医療・健康・投資・法律など高リスク領域に該当するか

**推奨クエリ:**
```text
{テーマ} 悩み 初心者
{テーマ} 実践 方法
{テーマ} 本 おすすめ
{テーマ} 事例 企業 個人
{テーマ} 最新 2026
```

**出力:**

`.company/outputs/ebooks/{book-name}/_research/theme_research.md`

```markdown
# テーマリサーチ: {テーマ}

## Phase 0回答の要約
...

## 読者ニーズ
...

## 競合・類似コンテンツ
...

## 重要キーワード
...

## 差別化ポイント
...

## 企画への反映方針
...

## 注意すべきリスク表現
...
```

**完了条件:**
- Step 1のタイトル案、想定読者、本全体の方向性に反映できる具体材料がある
- リサーチ結果が `theme_research.md` に保存されている
- 現在性が重要なテーマでは、古い知識だけで企画しない

### Step 1: 企画自動決定

Phase 0回答とStep 0のテーマリサーチをもとに、以下を自動決定して `project.md` 草案と `progress.json` に保存する。

- タイトル案 3〜5個
- サブタイトル案 3〜5個
- 想定読者
- 読者の主な悩み
- 本書で得られるベネフィット
- 本全体の方向性
- 文体
- 画像密度
- 出力フォルダ名

複数案を作る場合も、最もKDP販売性・読者明確性・マンガ化適性が高い1案を自動採用する。承認待ちで停止せず Step 2 へ進む。

### Step 2: 詳細アウトライン

5章構成で詳細アウトラインを作る。

各章には以下を含める。

- 章タイトル
- 章のゴール
- 節見出し 5〜8個
- 各節で扱う論点
- 具体例・ケーススタディ案
- 入れる図解・挿絵案

アウトラインを `manuscript/_outline.md` または `progress.json` に保存し、ユーザー確認待ちで停止せず Step 3 へ進む。

## タイトルローマ字

## サブタイトルフリガナ

{著者名}

- 第1章 ...
- 第2章 ...

- 第5章 ...
- おわりに

{挿絵・図解の密度、画風、用途}

### Step 4: 本文執筆

本文は章ごとに作成し、`manuscript/` 配下へ保存する。

執筆ルール:

- 読者の悩みから始め、具体例、解説、実践手順、まとめの順で展開する
- 各章の冒頭に「この章で扱うこと」を自然な本文で入れる
- 各章の末尾に短いまとめを入れる
- 見出しは Markdown の `##` / `###` を使う
- EPUB化する場合、各 `###` の番号付き節は原則として改ページ開始にする。節の途中に不要な改ページを入れず、節冒頭の読み始めが揃うようにする
- 段落の字下げは原則1字分にする。変換CSSで2字下げにならないよう `text-indent: 1em` 相当を基準にする
- 画像差し込み位置には以下の形式でプレースホルダを入れる
- 画像の直下に説明キャプションを出さない。説明が必要な場合は、通常の本文として画像の前後に自然に書く

```markdown
![{短い説明}](../images/diagram_001.png)
```

文字量が足りない場合は、抽象論を増やすのではなく、事例・反論への回答・チェックリスト・実践ステップを追加する。

### Step 5: 画像設計

各章に標準 2〜5点の画像を設計する。

画像タイプ:

- **挿絵**: 読者の状況、章の導入、感情的な場面を表す
- **図解**: 概念整理、比較、ステップ、フレームワーク、チェックリストを表す

画像ごとに以下を決める。

- ファイル名
- 種別: `illustration` / `diagram`
- 本文内の差し込み位置
- 画像の目的
- 生成プロンプト（読者代理キャラクターの外見設定文を含める）

画像設計の最初に、本のテーマ・想定読者に合わせた「読者代理キャラクター」1名（＋必要なら案内役1名）の外見設定を確定し、`progress.json` の `recurring_characters` に記録する（例: `20代後半の女性会社員、黒髪ショートボブ、白いブラウス、丸みのある親しみやすいアニメ調デザイン`）。

配置ルール:

- 画像は、置いた直後または直前の本文で扱っている論点に対応させる
- 「共通フレームワーク図」は、初出箇所など本文上意味がある場所に限定する。同じ図を複数節へ繰り返し挿入して画像密度を満たした扱いにしない
- 各節に画像を入れる指定がある場合は、節ごとに本文内容へ対応した画像を用意する。共通図解の複製で代替しない
- 表やチェックリストは、読みにくい横長表にしない。EPUBではカード型、箇条書き、短い2〜3列表のいずれかに整理する
- 画像下の表示キャプションは原則禁止。`figcaption` を生成しない。必要な説明は本文で書く

### Step 6: ChatGPT Images 2.0 画像生成

画像生成プロンプトは本文内容と対応させる。

共通ルール:

- 挿絵は日本のアニメ・マンガ調で、ポップで親しみやすい画風にする。実写風・フォトリアル調、無機質なピクトグラム/フラットインフォグラフィック調は禁止（実写風の明示指示がある場合のみ例外）
- 挿絵には読者代理キャラクターを登場させ、「悩み→気づき→実践→成長」など読者が共感できる感情を表情・ポーズで表現する
- 読者代理キャラクター（＋必要なら案内役1名）の外見設定は Step 5 の最初に1回確定し、全画像のプロンプトへ同じ文言で埋め込んで書籍全体で見た目を統一する
- 図解はシンプルで読みやすい構成を保ちつつ、余白にデフォルメした読者代理キャラのリアクション（ひらめき・驚き・納得の表情）を小さく添えて、無機質な図にしない。ただし構造を伝える線・矢印・ラベルの視認性を最優先し、キャラクター装飾は図の隅・余白のみに配置する
- 不要な細かい文字を画像内に入れすぎない
- 画像は PNG で `images/` に保存する
- 生成後に、画像の意図・本文位置・実際の本文内容がずれていないか目視またはファイル検査で確認する

推奨サイズ:

- 本文挿絵: `1536x1024`
- 本文図解: `1536x1024`
- 表紙を同時に作る場合: `1024x1536`
- 表紙は `KDP出版用/cover.png` をマスターとして保存し、同じ寸法で `KDP出版用/cover.jpg` も必ず保存する

### Step 7: KDPメタデータ作成

`KDP出版用/` に以下を作成する。

1. `書籍情報.md`
2. `ジャンル・キーワード.md`
3. `書籍紹介文_HTML.html`
4. `cover.png`
5. `cover.jpg`

`書籍情報.md` の冒頭は、タイトルとサブタイトルをそれぞれ **日本語 → フリガナ → ローマ字** の順で、次の見出し名どおりに作る。

```markdown
## タイトル
{日本語タイトル}

## タイトルフリガナ
{全角カタカナ読み}

## タイトルローマ字
{ASCIIローマ字}

## サブタイトル
{日本語サブタイトル}

## サブタイトルフリガナ
{全角カタカナ読み}

## サブタイトルローマ字
{ASCIIローマ字}
```

- 日本語欄は正式なタイトル表記を保ち、日本語の句読点・中黒・疑問符・数字を削らない
- フリガナ欄は全角カタカナで作り、数字は読みをカタカナで書く
- ローマ字欄は半角英字と半角スペースだけを使い、値全体を `^[A-Za-z ]+$` に一致させる
- ローマ字欄ではカンマ、ピリオド、疑問符、感嘆符、コロン、セミコロン、中黒、ハイフン、スラッシュ、アポストロフィ、括弧、長音記号・マクロン等のダイアクリティカルマークを使わない
- ローマ字欄へ算用数字を残さず、数字も読みを英字で書く（例: `72時間` → `Nanajuuni Jikan`）
- `ローマ字タイトル（ヘボン式）` と `ASCII入力用` のように欄を分けず、上記の記号なしローマ字欄へ統一する

表紙を生成した場合は、PNGだけで完了せず、KDP申請用にJPEG版も保存する。macOSでは以下を使える。

```bash
sips -s format jpeg -s formatOptions 95 KDP出版用/cover.png --out KDP出版用/cover.jpg
```

`書籍紹介文_HTML.html` は KDP 商品説明欄に貼れる形式で、以下の構成にする。

1. `<h2>` フック
2. `<ul>` 共感リスト
3. `<h3>` + `<p>` 解決策
4. `<h3>` + `<ul>` 本書で得られること
5. `<h3>` + `<ul>` こんな方におすすめ
6. `<h3>` + `<p>` CTA
7. `<h3>` + `<ul>` 目次

### Step 8: 品質チェック

完了前に以下を確認する。

- `project.md` が存在する
- `_research/theme_research.md` が存在し、Step 1の企画へ反映されている
- `manuscript/` に7ファイルが揃っている
- 全体文字数が目標範囲に入っている
- 章ごとの文字量に極端な偏りがない
- Markdownリンク先の画像ファイルが存在する
- 図解・挿絵が本文の内容と対応している
- 挿絵がアニメ・マンガ調のポップな画風で、無機質なピクトグラム調になっていない
- 読者代理キャラクターの見た目が全画像で統一されている
- 同一の共通図解を複数節に繰り返して、節固有の画像や図解の代わりにしていない
- 画像下に「図解: ○○」などの表示キャプションが出ない。EPUB/XHTML内に不要な `figcaption` がない
- Markdown画像のaltテキストに不要な `図解:` 接頭辞を残していない
- 番号付きの各節がEPUBで改ページ開始になっている
- 段落の字下げが1字分相当で、2字下げになっていない
- 表やチェックリストがEPUB上で読みやすい形に変換されている
- `KDP出版用/` のメタデータ3点と、表紙を作成した場合の画像2点が揃っている
- `書籍情報.md` と `project.md` で、タイトルとサブタイトルがそれぞれ日本語 → フリガナ → ローマ字の順になっている
- タイトルとサブタイトルのフリガナ欄が空でなく、数字を含む場合も読みが全角カタカナで書かれている
- タイトルとサブタイトルのローマ字欄が `^[A-Za-z ]+$` に一致し、記号・数字・ダイアクリティカルマークを含まない
- 表紙を作成した場合、`cover.png` と `cover.jpg` が揃っている
- `ebook-to-manga` の入力として使える構成になっている

品質チェック結果は、総文字数、章別文字数、画像点数、未解決事項を含めて最終レポートへ記録する。未解決事項があっても処理不能でなければ完成扱いとし、成果物一式の生成を優先する。

## ebook-to-manga への接続

このスキルの出力フォルダは、`ebook-to-manga` のソースフォルダとして使う。

```
ebook-to-manga source = .company/outputs/ebooks/{book-name}/
```

マンガ化前提の場合は、本文中の重要な会話・事例・心理変化を多めに入れると、後工程のシナリオ化がしやすい。
