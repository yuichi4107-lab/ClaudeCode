### マルチPC作業ディレクトリ方針

- **作業指示・ドキュメント・通常のスクリプトでは、PC固有の絶対パスを原則として使わず、リポジトリルートからの相対パスを使う**
- 論理上の作業場所は `YNFactory-cc` のリポジトリルートとする
- 現在の物理パスは Mac が `/Users/yuichi/YNFactory-cc`、Windows が `C:\YNFactory-cc`
- PC固有の実パスは `YNFACTORY_ROOT` などの環境変数、LaunchAgent / Task Scheduler の起動ラッパー、各PCセットアップ手順のみに閉じ込める
- 通常の制作・入力整理・生活ログ・成果物作成は、Google Drive側の `YNFactory-cc` を作業ディレクトリとして行う。Drive側をPC間で共有される作業コピーとする
- GitHubへ送る必要があるコード・スキル・ルール・設定だけを、作業後にローカルGit作業ディレクトリへ同じ相対パスで反映し、ローカルGit側で `git commit` / `git push` する
  - Drive側に `.git/` を置かない。Drive側では `git commit` / `git push` / `git pull` を実行しない
  - MacのローカルGit作業ディレクトリは `/Users/yuichi/YNFactory-cc`、Windowsは `C:\YNFactory-cc`
  - `git pull` はローカルGit作業ディレクトリで行い、pull後にGitHub由来の更新をDrive側の同じ相対パスへ反映する
  - 成果物・入力データ・生活ログなどGitHubに送らないものはDrive側に残し、ローカルGitへ無理にコピーしない
- Drive側とローカルGit側の反映には `.company/scripts/sync_drive_git.py` を使う。スクリプトはローカルGit作業ディレクトリから実行する
  - コミット+プッシュ: `python3 .company/scripts/sync_drive_git.py commit-push -m "<コミットメッセージ>" <相対パス...>` でDrive側の変更をローカルGit側へ反映し、指定パスだけを `git commit` / `git push` する
  - pull+Drive反映: `python3 .company/scripts/sync_drive_git.py pull-sync` でローカルGit側へ `git pull --ff-only` し、取得したGitHub由来の更新をDrive側へ反映する
  - 同期だけ必要な場合は `drive-to-local` / `local-to-drive` を使う
- 毎日午前3時（Asia/Tokyo）のGit同期ルーティンは、ローカルGit作業ディレクトリで `.company/scripts/daily_git_sync.py` を実行し、コミット→push→pull の順で処理する。Drive側でGit操作しない。重複するcron / LaunchAgent / Task Schedulerを追加しない

### ZSlimバックアップ方針

- Google Drive同期はバックアップではない。削除・上書き・破損・競合コピーも同期されるため、復元用バックアップは別系統で持つ
- 現在のバックアップ先はこのPCに接続している `ZSlim`（Macでは `/Volumes/ZSlim`）
- ZSlimバックアップの標準手順は `docs/backup-zslim.md` を参照する
- 保持期間は日次7世代、週次8世代、月次12世代
- `.git_drivebackup` 削除、Drive競合ファイル削除、大規模な `git rm --cached` は実行直前に明示確認を取る

## 2. 自走モード（AI側で話を進める）

ユーザーが細かい手順を明示していない場合、AI側は **秘書 → CEO → 要件定義 → 実行 → 品質チェック** の役割を自律的に使い分け、話を前に進める。
ユーザーは原則として、方針承認・重要な判断・外部サービス操作・公開/送信/購入/削除・課金や認証に関わる操作の最終承認のみを行う。

- ユーザーに毎回細かい作業指示を求めず、AI側で作業分解・担当振り分け・実行・品質確認・差し戻しを行う
- 秘書は依頼内容を受け取り、CEOロジックで必要な担当（requirements-definer / executor / quality-checker / 調査担当など）へ振り分ける
- 実行中は、AI同士の検討内容を必要に応じて要約し、ユーザーには「決定事項」「成果物」「未解決の論点」「承認が必要な点」を中心に返す
- ユーザーが「進めて」「実装して」「入れて下さい」など明確に実行を依頼した場合は、その依頼を要件定義の承認として扱い、実行と品質チェックまで進めてよい
- ただし、公開・投稿・送信・購入・削除・本番環境への不可逆な反映・外部アカウント操作は、必ず直前にユーザーの明示承認を取る
- 作業後は quality-checker 視点で完了条件とリスクを確認し、85点未満ならAI側で改善してから報告する

## 3. 品質ループ（全作業で必須）

すべての作業は **要件定義 → 実行 → 品質チェック** の3ステップで行う。例外なし。

| ステップ | エージェント | 役割 |
|---|---|---|
| 1. 要件定義 | `requirements-definer` | ゴール・スコープ・完了条件・品質基準・工程分割を確定。**ユーザー承認後に次へ** |
| 2. 実行 | `executor` | 要件定義書（＋前回QAフィードバック）に基づき作業を実行 |
| 3. 品質チェック | `quality-checker` | 100点満点で採点 → **85点以上で合格**、未満なら改善指示してステップ2へ戻す |

### 要件定義で確定する項目

- ゴール（何を達成するか）
- スコープ（何をやって何をやらないか）
- 完了条件（具体的・検証可能なチェックリスト）
- 品質基準（作業内容に最適なチェック項目を自動選定）
- **工程分割**（複数ステップの場合、工程ごとの中間成果物と品質基準を定義）

### ループ上限と複数工程ルール

- 各工程ごとに **最大5回** まで実行→チェックを繰り返す。超過時はユーザーへ相談
- 複数工程の作業は最初に **全工程分の要件定義を一括** で行う
- 各工程の品質チェックは **その工程の品質基準のみ** で採点（不良品を次工程に流さない）
- 前工程が合格するまで次工程に進まない

### フロー図（単一・複数工程共通）

```
ユーザーリクエスト
    ↓
[requirements-definer] → 要件定義書 → ユーザー承認？ ─No→ 修正して再提示
    ↓ Yes
┌─→ [executor] → 成果物
│       ↓
│   [quality-checker] → スコア
│       ├─ 85点以上 → 次工程へ（最終工程なら完了報告）
└───────┴─ 85点未満（5回以内） → 修正
              └─ 5回超過 → ユーザー相談
```

## 4. ターミナル出力制限

- ターミナルで大量出力しない
- ログ出力は最大200行に制限してください。
- 巨大なファイルや node_modules は直接表示しないでください。
- `cat`、`find`、`ls -R`、`npm test`、`python` 実行などは、結果を **100〜200行以内** に制限する
- 長い結果はログファイルに保存し、画面には要約と最後の200行だけ表示する
- 生成画像やファイル一覧を確認するときは、全件表示せず、最新の **1〜5件だけ** 表示する
- 大量のログやbase64文字列は絶対に画面に出さない
